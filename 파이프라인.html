1. 크롤링

인포케어(infocare.co.kr) 법원경매 사이트에서 낙찰 데이터 수집 · Selenium 기반
scripts/full_crawling.py 크롤링 엔진

모든 크롤링 스크립트가 공유하는 핵심 엔진. 로그인부터 검색·페이지 순회·CSV 저장까지의 공통 로직을 담고 있으며, 직접 실행하는 파일이 아니라 다른 스크립트가 import해서 쓰는 라이브러리입니다.

핵심 함수
  • build_driver() — Chrome 드라이버 생성
  • login_and_go_to_total_search() — 로그인 + 통합검색 진입
  • generate_half_year_ranges_upto_today() — 반년 단위 검색 구간 생성
  • set_search_filters_and_search() — 지역/기간 필터링
  • crawl_current_result_pages() — 페이지네이션 순회 수집
입력 / 출력

입력: .env의 INFOCARE_USER_ID / INFOCARE_PASSWORD
출력: 없음 (호출자가 CSV 저장 담당)

scripts/auto_crawling.py 파이프라인

지역 하나를 CLI로 지정해 처음부터 끝까지 수동으로 재크롤링할 때 쓰는 스크립트. README "자주 쓰는 명령어"에도 등재된 표준 진입점입니다.

CLI 인자

--region (예: 서울, 부산, 경기 / 미지정 시 대화형 입력 요청)

출력

data/{지역}.csv

실행
$ python3 scripts/auto_crawling.py --region 서울
scripts/recent_update_main.py 레거시

오늘 기준 ±45일 범위만 재크롤링해 광주 지역 CSV에 신규분만 병합하던 스크립트. 지금은 automate_full_update.py의 전 지역 배치가 이 역할을 대신하는 것으로 보이며, README와 배치 스크립트 어디에서도 참조되지 않습니다.

대상 지역

광주 고정 (코드 내 CrawlConfig 기본값 직접 수정 필요, argparse 없음)

출력

data/gwangju_recent_4w.csv, data/gwangju.csv 갱신

scripts/crawl_update_raw_csv.py 인수인계용

DB 접속 없이, 기존 raw CSV의 마지막 매각일부터 오늘까지 전 지역을 재크롤링해서 raw CSV 자체를 갱신합니다. 자회사에 데이터만 전달할 때 쓰는 용도로, DATABASE_URL이 필요 없습니다.

CLI 인자

--raw-csv (필수) · --end-date (YYYY-MM-DD, 기본 오늘)

실행
$ python3 scripts/crawl_update_raw_csv.py --raw-csv data/export/raw_data.csv --end-date 2026-08-01
scripts/debug_region_options.py 디버그

인포케어 사이트의 지역 선택 드롭다운(addr_do)에 실제로 어떤 value/text가 들어있는지 브라우저로 열어서 확인하는 도구. 운영에는 필요 없고, 사이트 구조가 바뀌었는지 의심될 때만 사용합니다.

실행
$ python3 scripts/debug_region_options.py

2. 전처리

크롤링 원자료를 DB 적재 가능한 형태로 정제 · 용도 매핑 · 누락값 보정
scripts/batch_ltv_update.py 파이프라인 핵심

지역별 raw CSV를 중복제거·낙찰건 필터링·시도/시군구 분리·분기 계산·LTV 용도 매핑까지 한 번에 처리합니다. automate_full_update.py가 이 모듈의 process_file()을 그대로 가져다 씁니다.

핵심 함수
  • map_ltv_usage(usage, bank_dict) — 용도명 매핑, 없으면 "기타건물/기타토지"로 대체
  • process_file(file_path) — 단일 CSV 전체 전처리, 같은 경로에 덮어쓰기
입력

data/양행별_용도_리스트_최신.csv (용도 매핑 마스터)
지역별 raw CSV (data/{지역}.csv)

실행
$ python3 scripts/batch_ltv_update.py  # 인자 없음, data/{지역}.csv 전체 순회
scripts/fill_zero.py 파이프라인 핵심

크롤링 시 낙찰가/낙찰율이 0으로 비어 수집된 행을, 사건번호로 사이트에서 재검색해 실제 값으로 채워 넣습니다. 매칭되지 않는 행은 삭제됩니다.

핵심 함수
  • fill_zero_multiple_csvs(csv_paths) — 브라우저 세션 1회로 여러 CSV 순회 (automate_full_update.py가 사용)
  • find_matching_row() — 날짜/용도/소재지/물건번호 기준 매칭
입력

.env의 INFOCARE 계정, 대상 CSV

단독 실행 (argparse 아님, sys.argv 사용)
$ python3 scripts/fill_zero.py data/서울.csv
scripts/전처리.py 레거시

batch_ltv_update.py의 원형으로 보이는 스크립트. 세종 지역 경로가 코드에 하드코딩(data/세종.csv)되어 있어 다른 지역을 처리하려면 코드를 직접 고쳐야 합니다.

출력

data/세종.csv (5년치로 덮어쓰기), data/original/세종_전체원본.csv (백업)

scripts/create_usage_mapping.py 유지보수용

data/*.csv 전 지역 raw 데이터에서 등장하는 모든 "용도" 값을 모아, 은행별(광주/전북) LTV 용도 매핑 마스터 테이블을 새로 만듭니다. 원본 데이터에 처음 보는 용도가 등장했을 때만 수동으로 실행합니다.

출력

data/양행별_용도_리스트_최신.csv

실행
$ python3 scripts/create_usage_mapping.py

3. DB 적재

정제된 CSV를 Supabase Postgres로 적재 / 정비
backend/migrate_to_db.py 초기 세팅 전용

은행별 LTV 기준표 CSV를 ltv_standards 테이블에 적재합니다. 새 DB를 구성하거나 사용자 DB로 전환할 때 가장 먼저 실행하는 스크립트입니다.

입력

data/LTV_기준(광주은행).csv, data/LTV_기준(전북은행).csv

출력

ltv_standards 테이블

실행
$ python3 backend/migrate_to_db.py
주의 — 실행할 때마다 ltv_standards 테이블을 전체 삭제 후 CSV 기준으로 재생성합니다. 운영 중 실수로 재실행하면 DB에 저장해둔 LTV 변경값이 CSV 기준으로 초기화됩니다.
scripts/load_region_csvs_to_db.py 파이프라인 핵심

지역별 경매 원자료 CSV를 region_auction_records 테이블에 적재합니다. 사건번호 기준으로 upsert하므로 같은 데이터를 여러 번 넣어도 중복되지 않습니다.

CLI 인자
  • --append — 기존 데이터 유지, upsert만 (미지정 시 전체 삭제 후 재적재)
  • --file-pattern — 기본 *.csv (예: *_new.csv)
실행
$ python3 scripts/load_region_csvs_to_db.py                              # 전체 재적재
$ python3 scripts/load_region_csvs_to_db.py --append --file-pattern "*_new.csv"  # 신규분만 (automate_full_update.py가 이 방식 사용)
scripts/dedupe_region_auction_records.py DB 정비

region_auction_records에서 (지역파일, 사건번호, 매각일, 용도) 조합이 중복된 행을 찾아 최신 것만 남기고 정리합니다. 이상 데이터가 의심될 때만 수동 실행합니다.

CLI 인자

--delete — 실제 삭제 실행 (미지정 시 dry-run으로 개수/샘플만 출력)

실행
$ python3 scripts/dedupe_region_auction_records.py          # 점검만, 삭제 없음
$ python3 scripts/dedupe_region_auction_records.py --delete # 실제 삭제

4. Signal / 집계

지역·용도별 낙찰가율을 집계해 RED / YELLOW / GREEN 판정
scripts/build_signal_cache_from_db.py 파이프라인 핵심

DB의 region_auction_records + ltv_standards를 집계해 signal_cache 테이블을 만듭니다. 지역×용도별 3/6/12/36/60개월 평균 낙찰가율·건수를 계산하고, AI 호출은 하지 않는 순수 통계 로직입니다.

CLI 인자
  • --bank — 광주은행 / 전북은행 (반복 가능, 기본 둘 다)
  • --base-ym — 단일 기준월 (예: 202608)
  • --start-ym / --end-ym — 범위 지정 (과거 소급 재계산 시)
  • --append — 기존 행 삭제 없이 추가/갱신만
실행
$ python3 scripts/build_signal_cache_from_db.py                          # DB 내 전체 기간 재구축
$ python3 scripts/build_signal_cache_from_db.py --bank 광주은행 --base-ym 202608
scripts/calc_signal_from_csv.py 인수인계용

DB 없이 로컬 raw CSV 1개 + LTV 기준 CSV만으로 시그널을 계산해 CSV로 내보냅니다. 자회사에 데이터를 전달할 때 사용합니다.

CLI 인자

--raw-csv (필수) · --base-ym (기본 이번 달) · --banks · --out-dir (기본 data/export)

실행
$ python3 scripts/calc_signal_from_csv.py --raw-csv data/export/raw_data.csv --base-ym 202608
주의 — 웹 화면에서 LTV를 수정해도 이 스크립트가 참조하는 로컬 CSV는 자동으로 갱신되지 않습니다. 또한 판정 로직(check_signal_logic)이 backend/services.py의 로직을 별도로 이식한 것이라, 원본 로직이 바뀌면 이 파일도 수동으로 맞춰야 합니다.

5. 배치 / 자동화

위 단계들을 순서대로 실행하는 오케스트레이터
scripts/automate_range_update.py ★ 가장 많이 쓰는 파이프라인

종료일을 지정하면 그 날짜 기준 최근 N일(기본 50일)만 전 지역 크롤링→전처리→낙찰가 보정→DB적재→시그널 계산→AI 권고안 생성까지 한 번에 처리합니다. automate_full_update.py와 같은 단계를 그대로 거치되, 크롤링 시작일을 매번 코드에서 손으로 고치지 않아도 되도록 --end-date/--days로 매번 지정하는 방식입니다.

CLI 인자
  • --end-date (필수) — 기준 종료일. 20260801 또는 2026-08-01 형식
  • --days — 종료일 기준 며칠 전부터 크롤링할지 (기본 50일)
  • --regions — 쉼표로 구분한 지역 목록 (미지정 시 16개 지역 전체)
  • --skip-ai — AI 권고안 생성 단계 생략 (시간/비용 절약하고 싶을 때)
동작 방식

종료일 - days일을 시작일로 계산해, full_crawling.generate_half_year_ranges_upto_today(..., today=종료일)을 그대로 재사용합니다. 연도를 걸치는 구간(예: 12월 말 기준 50일 전 = 전년도 11월)도 자동으로 올바르게 나눠 처리됩니다. 시그널 캐시와 AI 권고안도 "오늘"이 아니라 지정한 종료일의 기준월로 계산됩니다.

실행
$ python3 scripts/automate_range_update.py --end-date 20260801                    # 6/12~8/1 자동 크롤링 + 전체 파이프라인
$ python3 scripts/automate_range_update.py --end-date 2026-08-01 --days 30      # 최근 30일만
$ python3 scripts/automate_range_update.py --end-date 20260801 --regions 서울,경기  # 특정 지역만
$ python3 scripts/automate_range_update.py --end-date 20260801 --skip-ai          # AI 권고안 생략
scripts/automate_full_update.py 월간 운영 (구버전)

크롤링부터 AI 권고안 생성까지 전 과정을 순서대로 실행하던 월 1회 운영용 마스터 스크립트입니다. 지금은 같은 단계를 그대로 수행하면서 시작일을 매번 지정할 수 있는 automate_range_update.py가 실무에서 더 많이 쓰입니다 — 이 파일은 크롤링 시작일이 코드에 고정돼 있어 매월 직접 수정해야 합니다.

7단계 흐름
  • step_crawling() — 16개 지역 전체 순회 크롤링 → data/{지역}_new.csv (이미 수집된 지역은 스킵)
  • step_preprocessing() — batch_ltv_update.process_file() 적용
  • step_fill_zero() — fill_zero.fill_zero_multiple_csvs()로 낙찰가 보정
  • step_load_db() — load_region_csvs_to_db(append=True, "*_new.csv")
  • step_build_signal_cache() — 은행별 signal_cache 재계산
  • step_ai_analysis() — RED/YELLOW 대상 AI 권고안 생성
  • step_cleanup() — 임시 _new.csv 파일 삭제
실행
$ python3 scripts/automate_full_update.py
확인 필요 — step_crawling()의 크롤링 시작일이 datetime(2026, 5, 1)로 코드에 고정되어 있습니다 (scripts/automate_full_update.py:40). 원래 relativedelta(months=1)로 자동 계산하던 부분이 주석 처리되어 있어, 매월 실행 전에 이 날짜를 손으로 갱신해야 하는지 확인이 필요합니다.

시그널 판정 알고리즘 (가장 중요한 규칙)

calculate_metrics()로 3/6/12/36/60개월 평균·건수를 구하고, check_signal_logic()이 가중평균 괴리 (3개월×5 + 6개월×3 + 12개월×2) / 10가 10%p 이상이면 RED, 5%p 이상이면 YELLOW로 판정합니다. 3개월 건수가 10건 미만이면 무시하고, 3/6/12개월 방향이 모두 같은 방향(전부 하락 또는 전부 상승)일 때만 시그널을 발동합니다. LTV보다 낙찰가율이 높은 방향(과담보)은 리스크로 보지 않아 GREEN 처리됩니다.

AI 권고안 캐시

FIXED_MONTHS = 3/6/12/36/60개월, BANK_CONFIG = 은행별 설정

동작 방식

캐시 TTL

RED = 24시간, YELLOW = 72시간, 그 외 = 168시간 (지역+용도+시그널 상태가 바뀌면 캐시 키도 새로 생성됨)

주의사항 모음

실수하기 쉬운 지점들 — 실행 전에 한 번씩 확인
automate_full_update.py의 크롤링 시작일이 고정값
scripts/automate_full_update.py:40의 start_date = datetime(2026, 5, 1)가 하드코딩되어 있습니다. 원래 자동 계산 로직(relativedelta(months=1))은 주석 처리된 상태라, 매월 실행 전에 이 값을 직접 갱신해야 했습니다. 이 문제 때문에 만든 것이 automate_range_update.py이며, --end-date/--days로 매번 원하는 구간을 지정하므로 코드를 수정할 필요가 없습니다.
migrate_to_db.py는 매번 전체 삭제 후 재생성
실행할 때마다 ltv_standards 테이블을 통째로 지우고 CSV 기준으로 다시 채웁니다. 운영 중인 DB에 실수로 재실행하면 그동안 화면에서 저장한 LTV 변경값이 CSV 기준값으로 되돌아갑니다. 새 DB 세팅 또는 DB 이전 시에만 사용하세요.
calc_signal_from_csv.py의 판정 로직은 수동 동기화 대상
backend/services.py의 check_signal_logic()을 pandas로 별도 이식한 것이라, 원본 로직이 바뀌면 이 파일의 로직도 손으로 맞춰야 합니다(코드 내 주석에 명시됨). 또한 웹 화면에서 LTV를 수정해도 로컬 CSV는 자동으로 갱신되지 않습니다.
인수인계용 스크립트는 DB/AI 키 없이 동작
crawl_update_raw_csv.py, calc_signal_from_csv.py, crawl_and_export.py, export_raw_csv.py, export_signal_csv.py, export_handoff_csv.py는 공통적으로 DATABASE_URL/OPENAI_API_KEY 없이 동작하도록 만들어져 있습니다. 자회사에 데이터만 전달하는 별도 목적의 스크립트 세트이며, 메인 운영 파이프라인과는 무관합니다.
전처리.py, recent_update_main.py는 레거시로 추정
README와 automate_full_update.py 어디에도 참조되지 않습니다. 각각 batch_ltv_update.py와 automate_full_update.py의 이전 버전/원형으로 보이며, 삭제 전에 실제로 더 이상 안 쓰는지 한 번 더 확인을 권장합니다.
